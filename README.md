# E-Commerce Selenium Automation Framework

A Java 17 automation framework for web testing with Selenium, TestNG, Cucumber, Maven, explicit waits, and the Page Object Model.

The current automated scenario uses [Sauce Demo](https://www.saucedemo.com/) to complete an end-to-end purchase: log in, add a backpack to the cart, enter checkout details, finish the order, and verify the confirmation message.

## Current capabilities

- Selenium 4 Chrome automation using Selenium Manager; no ChromeDriver path is configured.
- Cucumber feature execution through TestNG and Maven Surefire.
- A tagged Cucumber purchase scenario: `@ECOM_purchase`.
- Cucumber hooks that create a browser before each scenario and close it afterwards.
- Page Objects for login, products, cart, checkout, and order confirmation.
- Explicit waits for visible, clickable, and present elements.
- Chrome maximization at the start of every scenario.
- Chrome password-save, password-manager, and password-leak prompts disabled for stable login automation.
- Automatic yellow outlining of WebElements before Selenium performs an element operation.
- A `browser` system property, defaulting to Chrome.
- An optional `slow` system property for observing the test flow.
- `ThreadLocal<WebDriver>` driver storage, ready for future parallel execution.

## Test execution architecture

The active test path is Cucumber executed by TestNG:

```text
Maven Surefire
  → CucumberRunnerTest
    → purchase.feature (@ECOM_purchase)
      → CucumberHooks @Before
        → DriverFactory.initializeDriver(browser)
          → create and maximize Chrome
          → disable password-manager popups
          → add automatic element highlighting
          → store this thread's driver
      → PurchaseSteps
        → Page Objects
          → WaitUtils
            → Selenium WebDriver
      → CucumberHooks @After
        → DriverFactory.quitDriver()
```

### Cucumber runner

`CucumberRunnerTest` extends `AbstractTestNGCucumberTests`. This connection lets Maven Surefire discover the class as a TestNG test and lets Cucumber execute its scenarios.

Its configuration specifies:

| Setting | Current value | Meaning |
| --- | --- | --- |
| `features` | `src/test/resources/features` | Folder containing Gherkin feature files. |
| `glue` | `com.ecommerce.automation.stepdefinitions` | Folder containing Java implementations of feature steps. |
| `glue` | `com.ecommerce.automation.hooks` | Folder containing Cucumber setup and cleanup hooks. |
| `plugin` | `pretty` | Prints readable Cucumber output in the terminal. |

### Feature file and tag

`src/test/resources/features/purchase.feature` contains one purchase scenario. It is tagged:

```gherkin
@ECOM_purchase
Feature: E-commerce purchase
```

The `@` is part of the tag. When filtering, use `@ECOM_purchase`, not `ECOM_purchase`.

### Cucumber hooks

`CucumberHooks` manages the browser lifecycle for Cucumber scenarios:

- `@Before` reads the `browser` property and defaults it to `chrome`.
- `@Before` calls `DriverFactory.initializeDriver(browser)`.
- `@After` calls `DriverFactory.quitDriver()`.

The existing `BaseTest` serves the same lifecycle role for direct TestNG tests. The current Cucumber flow uses `CucumberHooks` instead of `BaseTest`.

## DriverFactory

`DriverFactory` is the single source of browser management.

| Method | What it does |
| --- | --- |
| `initializeDriver(String browser)` | Validates the requested browser, creates and maximizes Chrome, applies Chrome preferences, decorates the driver for highlighting, and stores it for the current thread. |
| `getDriver()` | Returns the current thread's active WebDriver. |
| `quitDriver()` | Closes the current thread's browser and removes its `ThreadLocal` reference. |

### Browser support

Chrome is the only browser currently implemented. Passing another browser name causes an `IllegalArgumentException`.

Chrome is started with `new ChromeDriver(options)`. Selenium Manager finds or downloads the compatible ChromeDriver automatically, so no executable path is configured.

### Browser stability and visibility

At startup, the factory:

1. Disables Chrome password-saving, password-manager, and password-leak prompts. These are browser UI popups, not web-page alerts, so disabling them makes login tests more stable.
2. Maximizes the window with `webDriver.manage().window().maximize()`.
3. Wraps Chrome in Selenium's `EventFiringDecorator`.

The event listener adds a yellow outline before a WebElement operation. The outline is visual-only; a highlighting failure is intentionally ignored so it cannot fail a real test action.

### Why ThreadLocal is used

`ThreadLocal<WebDriver>` gives each test thread its own browser instance. One test cannot navigate, modify, or close another test's browser. This design supports parallel execution when a TestNG parallel configuration is added later.

## Page Objects

Page Objects keep locators and page actions out of Cucumber step definitions. They receive WebDriver through their constructor and use `WaitUtils` before interacting with elements.

| Page Object | Current responsibility |
| --- | --- |
| `LoginPage` | Open Sauce Demo, enter credentials, and log in. |
| `ProductsPage` | Verify the inventory page, add Sauce Labs Backpack, and open the cart. |
| `CartPage` | Verify the cart and backpack, then start checkout. |
| `CheckOutPage` | Fill customer details, continue to overview, and finish the order. |
| `OrderConfirmationPage` | Verify the completed-order state and read the confirmation text. |

Assertions remain in `PurchaseSteps`; Page Objects return data or perform actions only.

## WaitUtils

`WaitUtils` creates a `WebDriverWait` for a Page Object and currently uses a default timeout of **1 second**.

| Method | Wait condition |
| --- | --- |
| `waitForVisibility(By locator)` | The element is present and visible. |
| `waitForClickable(By locator)` | The element is ready to be clicked. |
| `waitForPresence(By locator)` | The element is present in the DOM, even if it is not visible. |

### Slow mode

Pass `-Dslow=true` to add a one-second debug delay after visibility and clickability waits. This is helpful when learning, debugging, or observing yellow element highlights; it deliberately slows the test and should be omitted from normal CI runs.

## Purchase scenario

The `@ECOM_purchase` scenario maps to these actions:

1. Open Sauce Demo.
2. Log in with Sauce Demo's public `standard_user` / `secret_sauce` account.
3. Verify that the products page appears.
4. Add Sauce Labs Backpack to the cart.
5. Open the cart and verify the cart and backpack.
6. Start checkout.
7. Enter first name, last name, and postal code.
8. Continue and verify the checkout overview.
9. Finish the order.
10. Verify the confirmation state and the `Thank you for your order!` message.

## Running tests

### Prerequisites

- JDK 17 or newer.
- Maven on your `PATH`.
- Google Chrome installed.
- Internet access on the first run so Maven can download dependencies and Selenium Manager can resolve the browser driver.

### Run all discovered tests

```bash
mvn clean test -Dbrowser=chrome
```

Because Chrome is the default, this also works:

```bash
mvn clean test
```

### Run the tagged purchase scenario

```bash
mvn clean test -Dbrowser=chrome -Dcucumber.filter.tags="@ECOM_purchase"
```

### Run the tagged scenario in slow mode

```bash
mvn clean test -Dbrowser=chrome -Dslow=true -Dcucumber.filter.tags="@ECOM_purchase"
```

The `-D` arguments set Java system properties for this Maven run:

| Argument | Effect |
| --- | --- |
| `-Dbrowser=chrome` | Selects Chrome; this is also the default. |
| `-Dslow=true` | Enables the debug delay in `WaitUtils`. |
| `-Dcucumber.filter.tags="@ECOM_purchase"` | Runs only scenarios tagged `@ECOM_purchase`. |

## Checking results

The terminal ends with either:

```text
BUILD SUCCESS
```

or:

```text
BUILD FAILURE
```

After the run, Maven Surefire reports are under:

```text
target/surefire-reports/
```

The easiest report to read is usually `TestSuite.txt`. It contains a summary such as:

```text
Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
```

`TEST-TestSuite.xml` contains the same result in XML, mainly for CI and reporting tools.

`target/` is generated build output. Do not edit or commit it; it is already ignored by Git.

## VS Code

For a reusable Maven command in VS Code, create a named task in `.vscode/tasks.json` and run it through **Tasks: Run Task**. A task is the closest equivalent to an IntelliJ Maven Run Configuration because it keeps the exact Maven goal and system properties together.

## Current scope

The direct `UserPurchaseTest` class is retained as commented legacy code. The active test implementation is Cucumber + TestNG.

Useful future additions include configuration files for environments and test data, reporting, screenshots on failures, parallel TestNG suites, CI integration, and additional browser support.
