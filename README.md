# E-Commerce Selenium Automation Framework

A Java 17, Maven, Selenium, and TestNG automation framework. The current implementation automates a complete purchase journey on [Sauce Demo](https://www.saucedemo.com/): log in, add a backpack to the cart, complete checkout, and verify the confirmation message.

## Current capabilities

- Chrome browser automation using Selenium Manager; no ChromeDriver path is configured.
- TestNG test lifecycle with one browser session per test method.
- Configurable browser selection through a Maven system property; Chrome is currently supported.
- `ThreadLocal<WebDriver>` storage to keep each test thread's browser isolated for future parallel execution.
- Browser maximization on startup.
- Chrome password-manager and password-leak prompts disabled for stable login tests.
- Automatic yellow element outlines before WebElement operations, using Selenium's event listener API.
- Reusable explicit waits for visibility, clickability, and DOM presence.
- Page Object Model for login, products, cart, checkout, and order confirmation pages.
- A TestNG end-to-end purchase test.

## How the framework works

When Maven runs a TestNG test, the flow is:

```text
Maven / Surefire
  → UserPurchaseTest
    → BaseTest @BeforeMethod
      → DriverFactory.initializeDriver(browser)
        → start and maximize Chrome
        → apply Chrome preferences
        → wrap the driver for automatic highlighting
        → store the driver in ThreadLocal
    → Page Objects perform browser actions through WaitUtils
    → TestNG assertions verify expected outcomes
    → BaseTest @AfterMethod(alwaysRun = true)
      → DriverFactory.quitDriver()
        → close Chrome and remove the ThreadLocal value
```

### 1. `BaseTest`

Every test class extends `BaseTest`.

- `@BeforeMethod` reads `System.getProperty("browser")`.
- If the property is omitted or blank, it uses `chrome`.
- It calls `DriverFactory.initializeDriver(browser)` before every test method.
- `@AfterMethod(alwaysRun = true)` calls `DriverFactory.quitDriver()` after every test method.

`alwaysRun = true` is important: cleanup still runs if a test fails or is skipped, preventing leftover Chrome and ChromeDriver processes.

### 2. `DriverFactory`

`DriverFactory` is the single place that creates, retrieves, and closes browsers.

| Method | Responsibility |
| --- | --- |
| `initializeDriver(String browser)` | Validates the browser, creates Chrome, maximizes it, and saves the decorated driver for the current thread. |
| `getDriver()` | Returns the WebDriver associated with the current test thread. |
| `quitDriver()` | Quits the current thread's browser and removes its `ThreadLocal` reference. |

The factory supports `chrome` only. Any other value produces a clear `IllegalArgumentException`.

#### Why `ThreadLocal<WebDriver>` is used

`ThreadLocal` gives every running test thread its own WebDriver instance. This avoids one test navigating, changing, or closing the browser used by another test. It makes the driver layer ready for parallel TestNG execution later.

#### Chrome configuration

Chrome starts through `new ChromeDriver(options)`. Selenium Manager resolves the matching driver automatically, so this project does not set a `chromedriver` executable path.

The Chrome preferences disable password saving, password-manager prompts, and password-leak notifications. This prevents browser-owned login popups from interfering with Sauce Demo tests.

The browser is then maximized with:

```java
webDriver.manage().window().maximize();
```

#### Automatic yellow highlighting

The factory wraps Chrome with Selenium's `EventFiringDecorator`. Before an operation on a `WebElement`, its listener adds a yellow CSS outline. This is visual-only: if highlighting cannot be applied, the actual test action continues.

Because `DriverFactory.getDriver()` returns the decorated driver, Page Objects do not need repeated highlight code.

## Page Objects

Page Objects contain page-specific locators and actions. They do not contain TestNG assertions; assertions remain in test classes.

| Page Object | URL or screen | Current responsibilities |
| --- | --- | --- |
| `LoginPage` | `https://www.saucedemo.com/` | Open the site, enter username and password, click login. |
| `ProductsPage` | Inventory | Confirm the products page, add Sauce Labs Backpack, open the cart. |
| `CartPage` | Cart | Confirm the cart and backpack are displayed, begin checkout. |
| `CheckOutPage` | Checkout information and overview | Enter customer information, continue, confirm overview, finish the order. |
| `OrderConfirmationPage` | Checkout complete | Confirm the success state and read the confirmation message. |

Each Page Object receives the current `WebDriver` through its constructor. This keeps browser lifecycle management out of page classes.

## `WaitUtils`

`WaitUtils` creates a `WebDriverWait` for each Page Object and exposes these methods:

| Method | Waits until |
| --- | --- |
| `waitForVisibility(By locator)` | The element exists and is visible. |
| `waitForClickable(By locator)` | The element is ready for interaction. |
| `waitForPresence(By locator)` | The element exists in the DOM, even if it is not visible. |

The current default timeout is **1 second**. The class also supports an optional slow mode:

```bash
mvn test -Dslow=true
```

When enabled, slow mode adds a one-second debug delay after visibility and clickability waits. Use it only while observing or debugging a test; it intentionally makes the suite slower.

## Current end-to-end test

`UserPurchaseTest` extends `BaseTest` and verifies this scenario:

1. Open Sauce Demo.
2. Log in with the public demo account `standard_user` / `secret_sauce`.
3. Verify the products page is displayed.
4. Add Sauce Labs Backpack to the cart.
5. Open the cart and verify the cart and backpack are visible.
6. Start checkout.
7. Enter first name, last name, and postal code.
8. Continue to the checkout overview and verify it is displayed.
9. Finish the order.
10. Verify the confirmation view and the message `Thank you for your order!`.

## Running the tests

### Prerequisites

- JDK 17 or newer installed.
- Maven installed and available on your `PATH`.
- Google Chrome installed.
- Internet access on the first run so Maven can download dependencies and Selenium Manager can resolve a compatible driver.

### Run all tests

```bash
mvn test
```

Chrome is used by default.

### Explicitly select Chrome

```bash
mvn test -Dbrowser=chrome
```

`-D` passes a Java system property to the Maven test JVM. `BaseTest` reads it with `System.getProperty("browser")` and forwards the value to `DriverFactory`.

### Run in slow mode

```bash
mvn test -Dbrowser=chrome -Dslow=true
```

This is useful while learning the flow or watching the yellow element highlight. Do not use slow mode in regular CI execution.

### Run the purchase test only

```bash
mvn test -Dtest=UserPurchaseTest -Dbrowser=chrome
```

## Current scope and next steps

The framework currently focuses on a simple, maintainable Selenium/TestNG Page Object architecture. Cucumber dependencies are declared, but Cucumber feature files, step definitions, and runners have not yet been implemented.

Possible next improvements include environment-based configuration, test data management, TestNG suite files and parallel execution, screenshots on failure, reporting, and CI integration.
